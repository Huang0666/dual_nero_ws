# 协作说明

## 目标

这份文档用于约定：以后如何把 `dual_nero_ws` 的沟通、排障、代码修改、测试验证和文档维护尽量统一收进 Codex 工作流中，减少在多个聊天窗口和多个工具之间来回切换。

## 当前推荐协作模式

推荐把下面几类事情都直接放到 Codex 里处理：

- 问题分析
- 调试定位
- 代码修改
- 测试脚本调整
- 文档更新
- 阶段规划
- 会话恢复

不建议再把“分析在一个地方、改代码在另一个地方、文档写在第三个地方”拆开做。  
对当前这个硬件 + ROS 2 + 真机验证项目，统一上下文比工具数量更重要。

## 你负责提供什么

每次只需要尽量把这些信息告诉 Codex：

### 1. 现象

例如：

- 哪一步失败了
- 哪条命令失败了
- 哪个 action 没响应
- 哪个 topic 数据不对
- 哪个机械臂动作异常

### 2. 目标

例如：

- 想先打通 read-only
- 想继续做最小动作
- 想修复 action 执行
- 想整理阶段文档

### 3. 现场信息

尽量直接贴原始信息：

- 终端输出
- 报错栈
- 日志片段
- `ros2 topic echo` 结果
- `ros2 action` 返回
- 当前配置文件内容

### 4. 你已经试过什么

例如：

- 改过哪个参数
- 换过哪个 CAN 口
- 手动调过姿态
- 重新启动过哪个 launch

这一步很重要，能减少重复试错。

## Codex 负责什么

在这个仓库里，Codex 负责：

- 读代码和配置
- 判断问题更可能出在哪里
- 直接修改仓库文件
- 补测试脚本
- 补诊断输出
- 更新 README 和 `docs/`
- 生成下一步验证命令
- 维护阶段状态和恢复文档

如果问题还没完全解决，Codex 应该继续把当前状态收口，而不是只给一个泛泛建议后停住。

## 推荐单轮工作方式

每一轮建议按这个顺序：

1. 你描述问题或目标
2. 你贴日志、报错或现象
3. Codex 检查仓库并直接改代码或文档
4. Codex 给你最小验证命令
5. 你回传真实运行结果
6. Codex 继续修正并更新文档

这个循环比“先长时间讨论、后单独再改代码”更高效。

## 推荐提问方式

下面这些方式最省时间：

### 适合直接说的

- “左臂 read-only 成功了，右臂失败，报错如下……”
- “双臂最小动作第一次失败，第二次成功，我怀疑是初始姿态问题”
- “帮我把当前阶段收口成文档”
- “把这次结论写进 README 和 session_resume”
- “基于当前仓库，继续推进 P2”

### 不够好的说法

- “好像哪里有点问题，你看看”
- “你先分析一下，不要动代码”

如果你只是想讨论，也可以明确说“这轮先不要改代码，只做判断”。

## 推荐把哪些事长期交给 Codex

### 1. 代码与脚本维护

例如：

- `test_left_arm.py`
- `test_right_arm.py`
- `test_dual_arm.py`
- bridge 节点
- launch 文件
- 配置文件

### 2. 阶段文档维护

当前项目建议长期维护这些文档：

- [project_status.md](project_status.md)
- [known_issues.md](known_issues.md)
- [next_actions.md](next_actions.md)
- [migration_runbook.md](migration_runbook.md)
- [session_resume.md](session_resume.md)

### 3. 新聊天框恢复

每次切新聊天框前，优先看：

- [session_resume.md](session_resume.md)
- [project_status.md](project_status.md)

必要时，把 `session_resume.md` 里的上下文模板直接贴给新会话。

## 当前项目的推荐分工

### 你更适合负责

- 真实硬件操作
- 现场观察
- 插拔设备
- CAN 连接确认
- 机械臂安全确认
- 回传真实测试结果

### Codex 更适合负责

- 代码与配置修改
- 逻辑收口
- 日志增强
- 测试顺序设计
- 文档归档
- 阶段计划维护

## 关于插件的建议

当前这个项目不建议靠很多“聊天增强插件”来解决协作问题。  
更有效的做法是：把上下文和工作流固定在仓库文档里。

如果要补工具能力，优先级建议是：

### 第一优先级

- GitHub 相关能力

适合做：

- issue 管理
- PR 审阅
- 变更追踪
- 协作交接

### 第二优先级

- 文档工作流

其实当前仓库里的 `docs/` 体系已经足够，不一定需要额外插件。

### 不建议优先投入

- 大量聊天类插件
- 多套重复的知识库工具

对当前项目，这些通常不如“把文档写清楚、把状态写准”更有效。

## 当前项目的最小协作闭环

如果你想把大部分工作都转到 Codex，这个闭环最稳妥：

1. 你提出目标
2. 你贴真实结果
3. Codex 改代码
4. Codex 更新文档
5. Codex 给下一步命令
6. 你执行并回传结果

只要保持这个节奏，基本可以把“沟通 + 调试 + 改代码 + 收口”都统一在一处完成。

## 何时只讨论不改代码

下面这些情况可以先只讨论：

- 你还在比较两条技术路线
- 你只想确认风险和取舍
- 你还没有准备好上真机
- 你只想让 Codex 帮你判断下一阶段计划

这时可以直接说：

- “这轮只做方案判断，不改代码”
- “先帮我整理选项和风险”

## 何时应该直接让 Codex 动手

下面这些情况，通常直接改更高效：

- 问题已经定位到具体文件
- 需要加日志
- 需要补测试脚本
- 需要统一 cleanup 行为
- 需要补文档
- 需要把阶段结论落库

## 会话结束前建议做什么

每次告一段落时，建议至少完成这三件事：

1. 更新 [project_status.md](project_status.md)
2. 更新 [next_actions.md](next_actions.md)
3. 更新 [session_resume.md](session_resume.md)

这样下次无论是隔天继续、换电脑继续，还是换新聊天框继续，都不会丢上下文。

## 结论

对 `dual_nero_ws` 这种真机调试型项目，最推荐的方式不是“把沟通和编码分给不同 AI”，而是：

- 尽量统一在 Codex 中处理
- 用仓库里的中文文档保存状态
- 用最小验证命令推进
- 用真实运行结果驱动下一轮修改

这套方式比频繁切换聊天窗口更稳，也更适合长期维护。
